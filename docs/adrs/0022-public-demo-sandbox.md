# 0022. Public demo sandbox reuses the real authorization model with one additive containment rule

Status: Accepted

## Context

A portfolio visitor needs to experience the real product - create/evaluate/promote/review, both sides of a promotion - without a private credential, and without being able to touch the curated Orion Commerce data every other doc/screenshot in this repo depends on staying stable. The brief was explicit: this must be a real interactive sandbox against the real backend/database/agent-eval, not a mocked frontend, and every existing authorization rule (RBAC, no-self-approval, stale-evidence blocking, single-production-version) must keep working exactly as it does today.

Inspecting `app/services/permissions.py` found the mechanism already mostly existed: `can_create_agent`, `can_request_evaluation`, `can_request_promotion`, and `can_grant_mcp_tool` all already restrict a **Builder** to their own `team_id`. The real gap was **elevated roles** (`Reviewer`, `Admin`): by design (ADR-0010, "why global roles, not per-team roles"), a real Reviewer/Admin's authority is *not* team-scoped - Jordan (SRE) can legitimately review Maya's (AI Platform) request. That is correct and load-bearing for the real organization, but it means a public-facing demo Reviewer account, given the same role, would - by the existing, correct design - be able to approve or reject a real Orion Commerce promotion request. That gap had to be closed without touching the real semantics real users depend on.

## Decision

- **A dedicated team** ("Public Demo Sandbox") and **two dedicated identities** (`demo-builder@agent-platform-demo.example`, Builder; `demo-reviewer@agent-platform-demo.example`, Reviewer) - never the canonical Maya/Jordan/Priya/Alex accounts, never granted Admin. Real Identity Platform accounts, signed in via the same `POST accounts:signInWithPassword` flow every other user uses (`app/api/auth/login-demo/route.ts` reuses `login-password`'s helper) - a genuine sign-in, just with the credential supplied by the server instead of typed by the visitor (the credential isn't a secret worth protecting; the account's blast radius is what's contained, below).
- **One additive authorization function**, `permissions.demo_containment_ok(user, target_team_id)`: a no-op (`True`) for every real Orion user, and for a demo-team actor, `True` only when `target_team_id` is the demo team's own id - regardless of role. Wired into every real write path a demo actor could reach: `create_agent_version`, `request_evaluation`, `request_promotion`, `approve_promotion`, `reject_promotion`, `grant_capability`, `revoke_capability`. This is checked *in addition to*, never instead of, each function's existing `can_*` check - a demo actor still needs the normal permission (Reviewer role to decide, no self-approval, etc.) **and** containment.
- **Guardrails specific to the demo's real external calls** (`app/services/evaluations.py::_enforce_demo_evaluation_guardrails`): a fixed, known-safe `external_agent_version_id` (rejects anything else), a per-actor cooldown, and a global concurrency cap - bounding real load/cost on `agent-eval-api`/Cloud Tasks regardless of public traffic, without inventing a generic rate-limiting framework.
- **Visibility, not just writes**: the dashboard's counts/"Needs Attention" and the global promotion-request queue apply one binary demo/non-demo bucket split (`app/services/dashboard.py::_demo_visibility_clause`) - a demo actor sees only the demo team's own data, a real Orion actor never sees the demo team's. The dashboard's global recent-activity feed goes further: a demo actor sees none of it at all (real internal Orion audit history has no business appearing to a public visitor); a real Orion actor's feed is unfiltered, including any demo activity, preserving the existing full-transparency guarantee for trusted internal staff. The dedicated `/activity` full audit page and each entity's own detail-page activity sidebar remain unfiltered for everyone, by design - ground truth is ground truth, and an agent's own page already only ever shows its own events.
- **Reset, not deletion**: `app/services/demo.py::reset_demo_environment` never deletes anything (consistent with this platform's real no-deletion philosophy throughout) - it closes long-abandoned pending requests via the real `reject_promotion` path and creates a fresh draft `AgentVersion` so a new visitor always has somewhere to start. Runs on a Cloud Scheduler cadence and on-demand (Admin-authenticated).

## Alternatives considered

- **A second, simplified "demo mode" API or mocked frontend.** Rejected outright by the brief - the whole point is a real interactive sandbox, and a parallel code path would drift from the real one immediately.
- **Team-scoping elevated roles globally** (removing the Reviewer/Admin cross-team bypass entirely). Rejected - that bypass is correct, intentional behavior for the real organization (ADR-0010); weakening it to solve a demo-specific problem would be the tail wagging the dog.
- **A `demo_role` flag on `Role` instead of a dedicated team.** Rejected - team membership already carries exactly the scoping semantics needed (`team_id` comparisons already exist everywhere), and introducing a second identity dimension would mean auditing every `Role`-based check in the codebase for whether it also needs to consult the new flag. A team is data, not a new authorization primitive.

## Consequences

Every write path a demo actor can reach now carries one extra, cheap check; every non-demo actor's behavior is provably unchanged (the check is `True` unconditionally unless `settings.demo_team_id` is set and the actor belongs to it - unset in every environment before this phase, including all existing tests). The real cost: any *future* write path added to the platform must remember to add the same `demo_containment_ok` check if it's reachable by a Builder/Reviewer/Admin acting on a specific Agent/team - there is no single enforcement point (like a DB-level policy) that would catch a forgotten call site automatically. Documented here as the tradeoff accepted for reusing the real, simple, already-proven permission model instead of building a second one.
