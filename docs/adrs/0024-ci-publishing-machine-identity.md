# 0024. CI publishing uses a dedicated machine identity, structurally separate from human RBAC

Status: Accepted

## Context

Phase 8's provenance correction (ADR-0023) requires that an integrated agent's `AgentVersion`s be created by its own CI after a real build, not typed in by a human. That means a genuinely new kind of caller exists: not a Viewer/Builder/Reviewer/Admin acting through Identity Platform, but a CI pipeline acting on behalf of a specific repository. The brief is explicit that human RBAC and machine/service authentication must stay conceptually distinct, and that a long-lived credential file is unacceptable - this project has held that line for every service-to-service relationship so far (`agent-platform-api` → `agent-eval-api`, Cloud Tasks/Scheduler → `agent-platform-api`), all via short-lived, real Google-signed OIDC tokens, never a downloaded key.

## Decision

A dedicated service account, `agent-platform-ci-publisher@ai-ops-center-eb26.iam.gserviceaccount.com`, is the only identity that may call `POST /internal/ci/agents/{agent_id}/versions` (`app/api/ci_publish.py`). Verification (`app/auth/ci_publisher.py::verify_ci_publisher`) is the same real mechanism already proven for Cloud Tasks/Scheduler pushes (`app/auth/cloud_tasks.py`, ADR-0021): a genuine Google-signed OIDC token, checked against Google's own certs, the expected audience, and the caller's exact service-account `email` claim - deliberately implemented as a second, independent function rather than refactored to share code with `verify_cloud_tasks_push`, so nothing about this new, smaller-blast-radius identity can accidentally weaken the already-proven Cloud Tasks path.

This identity is never a `User` row, never holds a `Role`, and the endpoint it calls is structurally separate from every human-facing route - `app/api/agents.py`'s `POST /v1/agents/{id}/versions` always calls `create_agent_version` with `via_ci=False` (the default); only `app/api/ci_publish.py` ever passes `via_ci=True` with a validated `provenance` block. **Live-verified**, not just reasoned about: a real OIDC token was minted for this service account and used to publish a real `AgentVersion` (with the real `ai-operations` commit SHA as provenance) against the real deployed backend; a real human Identity-Platform JWT was independently confirmed rejected by the same endpoint (`401`, Google's OIDC verifier correctly refuses a token from a different signing infrastructure); and a real human JWT was confirmed rejected attempting to manually create a version for the now-CI-integrated test agent via the ordinary human route (`403`), proving the lockout in ADR-0023 is real, not just implemented.

For the real `GitHub Actions` → this service account trust relationship specifically (as opposed to the service account existing and being verifiable, which is proven above): Workload Identity Federation, trusting GitHub's own OIDC issuer for the specific `ai-operations` repository/workflow, scoped to mint tokens only as this one service account - not yet built as of this ADR (see `docs/phase-notes/phase-8.md` for what remains open). The service account, the endpoint, and the verification logic are all real and working today; only the "a GitHub Actions run can obtain a token for this identity without a human in the loop" leg remains, since that requires touching `ai-operations`' own repository (pushing its pending commits, adding a workflow file) - explicitly held for the user's sign-off before doing so, per this project's standing rule about actions that cross a repository boundary.

## Alternatives considered

- **A long-lived API key or downloaded service-account key file for CI.** Rejected outright - every other machine-to-machine relationship in this project deliberately avoids exactly this (see ADR-0016's "no service-account key file was ever downloaded or persisted" for the agent-eval integration), for the same reason: a downloaded key is a standing secret that can leak and has no natural expiry, where a short-lived OIDC token minted per-run does not.
- **Reuse the Cloud Tasks/Scheduler service account (`agent-platform-tasks`) for CI publishing too**, since the verification mechanism is identical. Rejected - that identity's whole purpose is "this platform's own internal jobs calling back into itself" (outbox sweep, evaluation dispatch); CI publishing is a fundamentally different trust relationship (an external repository's pipeline, not this platform's own internal scheduler), and collapsing them would make an IAM audit of "who can do what" less legible for no real savings.
- **Model CI as a special `User` row with a `Role`.** Rejected - `Role` (`docs/auth-and-approval-model.md`) is specifically the human authorization model (Viewer/Builder/Reviewer/Admin, team-scoped). Forcing CI into that shape would blur exactly the "keep human RBAC and machine identity conceptually distinct" line the brief drew, for a caller that doesn't actually need or want any of RBAC's team/role semantics - it needs exactly one capability, on exactly one endpoint.

## Consequences

Adding a second CI-integrated agent later reuses this same service account and endpoint unchanged (the endpoint is already parameterized by `agent_id`); no new machine identity is needed per agent. The real gap this ADR leaves open - GitHub's OIDC issuer trusted via Workload Identity Federation, scoped to `ai-operations`' specific repository - is the one piece of Phase 8 that requires touching another repository's CI configuration and pushing its pending local commits, and was deliberately left for explicit confirmation rather than done unilaterally.
