# Phase 4 Notes: Promotion Requests, Human Review, Production Promotion, Rollback

Status: complete. `candidate/retired → production` (human promotion approval, including rollback) is fully implemented, tested, and live-verified against the real dev Postgres database and the real deployed `agent-eval-api` Cloud Run service. Frontend work (Phase 5) not started, per the stop condition.

## Implementation summary

Built the service (`app/services/promotions.py`) and API (`app/api/promotions.py`) layer that actually uses the `PromotionRequest`/`PromotionDecision` tables and no-self-approval DB trigger that have existed, unit-tested but unused, since Phase 1. `PromotionRequest` was extended (migrations `0014`/`0015`) to capture the full decision context at request time rather than just `agent_version_id` - evaluation reference/policy, a fresh capability-grant snapshot, the production version at request time, and a full freshness snapshot - per the brief's explicit instruction not to assume that context can always be reconstructed later. A second, independent freshness snapshot is taken live at decision time. Production promotion is one atomic transaction: authority checks, a per-Agent advisory lock, freshness/gate/lifecycle re-verification, the actual stage transition (including retiring the previous production version), the `PromotionDecision`, `AuditEvent`s, and a transactional outbox row, all committed together or not at all. A new `OutboxEvent` table (migration `0016`) and `EventPublisher` abstraction (`app/services/event_publisher.py`) close a gap named back in Phase 0/3's roadmap: promotion events are now genuinely fanned out to Pub/Sub, not just recorded in `audit_events`.

## PromotionRequest / PromotionDecision model

See [ADR-0018](../adrs/0018-promotion-request-immutability.md) for the full reasoning. In short: `PromotionRequest` gained `evaluation_run_reference_id`/`evaluation_policy_id` (now `NOT NULL`), `capability_grant_snapshot_hash`/`capability_grant_snapshot`, `production_version_id_at_request`, and `freshness_snapshot` - a frozen "eligible when requested" fact. `PromotionDecision` gained `freshness_snapshot_at_decision` - a second, independent "eligible when reviewed" fact, recomputed live, never reusing the request's own snapshot. Both tables are immutable at the DB level: `PromotionRequest` via column-level `GRANT UPDATE (status)` only (migration `0015`, mirroring `AgentVersion`/`SkillVersion`/`EvaluationPolicy`'s established pattern but adapted since `status` genuinely must transition), `PromotionDecision` fully immutable like `AuditEvent`.

`PromotionRequestStatus` stays `pending/approved/rejected` (plus the pre-existing, still-dormant `withdrawn`) - no new status was added for "stale" or "invalidated." Staleness is a live-computed property (`currently_eligible`), never a stored, eventually-inconsistent field.

## Request / approval / rejection semantics

**`request_promotion`**: permission check (`can_request_promotion` - Builder own-team-or-above, Reviewer/Admin any team), lifecycle-stage check (`candidate` or `retired` only), duplicate-pending check (proactive `SELECT`, backed by the partial unique index as the real invariant - a caught `IntegrityError` on the race is translated to a `409`, never leaked as a raw DB exception), then the live freshness gate: a `PromotionRequest` cannot be *created at all* if `currently_eligible` is false, per [ADR-0008](../adrs/0008-automated-gates-vs-human-approval.md)'s existing "gates are hard blockers, not created-and-pending" decision. Only once all of that passes is the full context snapshot taken and the row written.

**`approve_promotion`**: the brief's 10-step sequence, in order - validate reviewer authority (`can_decide_promotion`, defense-in-depth ahead of the DB trigger), acquire `pg_advisory_xact_lock(hashtext(agent_id))`, re-check `status='pending'` under the lock, re-verify the AgentVersion is still `candidate`/`retired`, re-verify the cited `EvaluationGateResult`s still all pass (defense-in-depth; expected unreachable since gate rows are immutable), re-check freshness **live, a second time** (blocks with no mutation if stale - `promotion.approval_blocked_stale` audit event), identify the current production version, transition the candidate to `production`, transition the previous production version to `retired`, persist the `PromotionDecision`, emit `AuditEvent`s, write the outbox row, commit, then publish (best-effort, after commit).

**`reject_promotion`**: same authority/locking, but never blocked by staleness - a Reviewer may reject a still-pending request for any reason. `freshness_snapshot_at_decision` is still recorded, so the rejection reasoning is auditable against exactly what evidence state the reviewer actually saw. No lifecycle mutation - see "Rejection semantics" below.

## Rejection semantics: candidate stays candidate

Decided by reading the state diagram literally, not by picking whichever was easier to code: there is no `candidate -> draft` edge anywhere in this platform's documented promotion lifecycle (`docs/evaluation-and-promotion.md`, `docs/adrs/0007-promotion-state-machine.md`). A rejected request's `AgentVersion` stays exactly where it was. A Builder can file a fresh `PromotionRequest` against the same version once the rejected one is no longer `pending` - the partial unique index only blocks a *second concurrently-pending* request, not a resubmission after rejection. Live-verified: `docs/phase-notes/phase-4.md`'s own live demo 4, below.

## Rollback semantics

Rollback is not a special mutable rollback state - it is an ordinary `PromotionRequest` with `from_stage=retired`, gated through the exact same `request_promotion`/`approve_promotion` path as any other promotion, including the same live evidence-freshness and gate checks (`docs/open-questions.md` #2, resolved by [ADR-0007](../adrs/0007-promotion-state-machine.md)'s Phase 4 update: gates stay hard even for rollback, no bypass). `check_freshness` gained a `promotable_stages` parameter (`{candidate}` by default, unchanged for the existing candidacy endpoint; `{candidate, retired}` for promotion requests) so the same function serves both cases without duplicating freshness logic. As of this phase, the only path to `retired` is automatic supersession during a promotion - a standalone manual abandon action was not built (out of this phase's actual scope; see the roadmap note).

## Production transition: atomicity and concurrency

One transaction, and - a real bug caught by testing, not just reasoned about - retiring the old production row and promoting the new one had to become two separately-`flush()`ed statements, in that fixed order, rather than one batched update. Postgres checks the partial unique index (`UNIQUE (agent_id) WHERE stage='production'`) immediately per row, not deferred to transaction end; batching or promoting-before-retiring can transiently put two rows at `production` at once and get rejected, even though the *final* state after both updates is perfectly valid. Retire first, then promote, both inside the one transaction that ultimately commits or rolls back together.

Concurrency protection is a `pg_advisory_xact_lock(hashtext(agent_id))`, acquired at the start of the decision, before re-reading the request's status - not Postgres `SERIALIZABLE` isolation (the hazard is a plain concurrent-UPDATE conflict, not a phantom-read anomaly, so `SERIALIZABLE`'s retry-loop requirement isn't needed) and not a row-level `SELECT ... FOR UPDATE` (one decision can touch two different `AgentVersionLifecycle` rows, and the second may not exist yet when the lock must already be held). The partial unique index remains the final DB-level backstop exactly as [ADR-0007](../adrs/0007-promotion-state-machine.md) originally called for. See [`evaluation-and-promotion.md`](../evaluation-and-promotion.md#concurrency-an-advisory-lock-not-serializable) for the full writeup and the "Live verification" section below for the real two-session proof.

## Authorization

Reused Phase 1's existing `permissions.py` functions unchanged - `can_request_promotion` (Builder own-team-or-above, Reviewer/Admin any team) and `can_decide_promotion` (Reviewer/Admin, and explicitly never the requester). No new authorization function was needed for approve vs. reject; both require the same authority, matching the brief's own framing ("Reviewer/Admin who is not the requester" applies identically to either decision). Negative cases test-verified: Viewer requesting promotion (403), Builder self-approving (403, blocked by role before the self-approval check even applies), Builder from another team requesting (403), Reviewer approving their own request (403, `can_decide_promotion`'s explicit `user.id == requested_by_user_id` check - backed by the DB trigger as the real, unbypassable guarantee), and unauthorized rejection (403). Authorization and evidence checks are kept strictly separate, as instructed: a 403 never depends on freshness, and a freshness-blocked approval is a 409, never a 403.

## Audit and event behavior

New event types: `promotion.requested`, `promotion.approved`, `promotion.rejected`, `promotion.approval_blocked_stale` (a real attempted action that was denied - useful audit signal even though nothing mutated), `promotion.rollback` (emitted alongside `agent_version.promoted` specifically when `from_stage=retired`, so rollbacks are trivially queryable without parsing payloads), `agent_version.promoted`, and `agent_version.retired` (on supersession). See [`audit-model.md`](../audit-model.md) for the full catalog and payload shapes. All audit writes remain in the same transaction as the state change they describe, per the existing (unchanged) Phase 1-3 guarantee.

The Pub/Sub outbox decision: implemented for real this phase, not deferred to Phase 6, per the roadmap's own Phase 4 scope note. `OutboxEvent` rows are written inside the exact same transaction as the production transition; publishing to the real `agent-platform-events` topic happens strictly after commit, best-effort (a publish failure is recorded on the row, never raised back to the caller, since the promotion itself already succeeded). See [ADR-0020](../adrs/0020-promotion-lifecycle-event-outbox.md). Scoped to `agent_version.promoted` only - not a general audit-event-to-Pub/Sub fan-out, which remains future work.

## Bugs discovered

1. **Retire-before-promote ordering** (see "Production transition" above) - a real `UniqueViolationError` against the actual partial unique index, caught by `test_rollback_full_history_preserved`, fixed by splitting one flush into two, in order.
2. **`entered_at` never updated on lifecycle stage transitions** - `AgentVersionLifecycle.entered_at` (`server_default=func.now()`, no `onupdate`) only ever reflected row-creation time, not the actual entry time of the current stage, in the pre-existing Phase 3 worker code (`evaluation_worker.py`'s `draft`/`candidate` transitions). Fixed by explicitly setting it alongside `entered_by` at every transition site (worker and promotions service) - a one-line fix per site, needed because Phase 4's audit answer ("when did this become production") depends on it being accurate.
3. **A real, untracked grants gap in the migration history** - discovered while granting `outbox_events` to `agent_platform_app`: every other table's grants trace back to a one-time, untracked `GRANT ALL ON ALL TABLES IN SCHEMA public` run directly against the DB at some point in an earlier phase, never captured in any Alembic migration. A brand-new table gets nothing until granted explicitly. Migration `0016` grants `outbox_events` explicitly, with this finding documented in the migration itself; earlier migrations were not retroactively fixed (out of scope, risk of rewriting applied history).
4. **Test-writing bugs, not production bugs**, worth naming since they cost real debugging time: (a) creating a second `EvaluationPolicy` version for the same agent name in a test made an *already-passing* version's evidence `policy_changed`-stale - a correct platform behavior, wrong test setup; (b) the real deployed `agent-eval-api` validates `agent_version_id` against its own registered `AgentVersion` catalog (`GET /agents`), rejecting an arbitrary string/UUID - a real, useful API-contract finding for live verification scripts, not a platform bug (this platform's own `external_agent_version_id` is deliberately opaque; agent-eval enforcing referential integrity on its own side is its business, not this platform's).
5. **Environment mistake, corrected**: an early `pip install google-cloud-pubsub` was run with the wrong `pip` (the global conda `base` environment's, not the project's `uv`-managed `.venv`) before the mistake was caught, upgrading `protobuf`/`requests`/`google-auth` etc. globally in a way that breaks `streamlit`'s pinned `protobuf` range. The correct install (`uv pip install --python .venv/bin/python ...`) was then used for the actual project dependency (added to `pyproject.toml`). Reverting the global conda environment change was attempted but declined by the auto-mode permission classifier as a package-removal action outside this project needing explicit confirmation - **flagged here and in the final report for the user to address**, not silently left unmentioned.

## Live verification

All of this was run against the **real** dev Postgres database (`agent_dev_platform_dev`) and the **real** deployed `agent-eval-api` Cloud Run service (`https://agent-eval-api-zndywutdxa-uc.a.run.app`, real impersonated-credentials auth), using the real seeded Orion Commerce users (Maya Chen/builder, Jordan Brooks and Priya Shah/reviewers, Alex Rivera/admin) - no fakes, no mocks, for every scenario below.

0. **`incident-investigator@4.2.0`'s real organic staleness.** Before touching anything else, its live candidacy was re-checked: `historically_passed=true`, `currently_eligible=false`, `capability_grants_changed` (real drift in its capability grants since Phase 3's own live verification - not staged for this demo, a genuine finding about how freshness behaves on real data over real elapsed time). Left alone rather than manipulated back into eligibility, since the goal was proving the promotion flow, not re-doing Phase 3.
1. **A dedicated live-demo Agent**, with four real candidate `AgentVersion`s, each evaluated for real against the deployed `agent-eval-api`'s real registered `stub-agent` target (fast, deterministic - `completion_check` evaluator, `stub-agent-smoke-v1` dataset) and a real `EvaluationPolicy` calibrated to that dataset's real, observed 6/7 pass rate.
2. **Successful promotion, Reviewer != requester**: Maya (builder) requested promotion of `v1.0.0`; Jordan (reviewer, a different person) approved it. `v1.0.0` reached `production` for real.
3. **A second promotion supersedes the first**: Maya requested promotion of `v2.0.0` (`production_version_id_at_request` correctly recorded `v1.0.0`'s id); Priya approved it. `v1.0.0` → `retired`, `v2.0.0` → `production`, in the real DB.
4. **Rejection, candidate stays candidate**: Maya requested promotion of `v3.0.0`; Jordan rejected it. `v3.0.0` remained `candidate` afterward.
5. **Rollback with full history preserved**: Maya requested promotion of `v1.0.0` again (now `retired` - `from_stage` correctly recorded as `retired`); Priya approved it. `v1.0.0` → `production` again, `v2.0.0` → `retired`. A real `promotion.rollback` audit event was recorded.
6. **Stale-evidence block, no production mutation**: Maya requested promotion of `v4.0.0` (fresh, `currently_eligible=true` at request time); a real new capability grant was then added to `v4.0.0`; Priya's approval attempt was correctly blocked (`409`, `capability_grants_changed`), `PromotionRequest.status` remained `pending`, and `v4.0.0`'s lifecycle stage remained `candidate` - no production mutation occurred.
7. **Full promotion history**, queried via `list_promotion_history_for_agent` against the real data above: all five requests present, in order, each with its correct decision, from and to stage, and status - reconstructing exactly why `v1.0.0` is in production right now without needing anything beyond this table and its linked decisions.
8. **Pub/Sub outbox, real end to end**: a real `OutboxEvent` row was published via `PubSubPublisher` to the real `agent-platform-events` Pub/Sub topic (created this phase in `ai-ops-center-eb26`); a real `gcloud pubsub subscriptions pull` against a temporary verification subscription confirmed the exact message actually arrived (not just that the publish call returned success) - the verification subscription was deleted afterward, the topic itself kept as real, permanent infrastructure.
9. **Concurrency, proven with a real two-session test** (`tests/test_promotions.py::test_concurrent_approvals_for_same_agent_only_one_ends_in_production`) rather than manual reproduction, per the brief's explicit allowance - two genuinely concurrent `approve_promotion` calls, separate database sessions/connections, for two different candidates of the same `Agent`, against the real Postgres constraint and advisory lock. Exactly one version ends in `production`.
