# Phase 7 Notes: Public Interactive Demo Sandbox

Status: complete. A real, fully interactive public demo - two dedicated Identity Platform identities, contained to their own Agent by a new, additive backend authorization rule, walking the genuine create -> evaluate -> promote -> review lifecycle against the real deployed backend/database/`agent-eval-api`. No mocked frontend, no shortcut authorization path. This was requested directly by the user after Phase 6's closure ("Add a 'Continue as demo user' flow... Do not make the public demo read-only... Design a sandboxed interactive demo environment using the existing authentication and authorization model"), not part of the original six-phase plan.

## What was built

- **`Public Demo Sandbox` team**, two real Identity Platform accounts (`demo-builder@agent-platform-demo.example` / Builder, `demo-reviewer@agent-platform-demo.example` / Reviewer - never the canonical Orion Commerce accounts, never Admin), and one dedicated Agent (`public-demo-agent`) and `EvaluationPolicy` (`public-demo-agent@v1`, mirroring the real `incident-investigator@v1` policy's dataset/evaluator so the demo evaluates against the same real, safe agent-eval stub used throughout this project's own verification). Seeded via `scripts/seed_demo_sandbox.py`, idempotent, creating the Agent/Policy through the real `agents`/`evaluation_policies` service layer (not direct DB writes) exactly like `seed_orion_commerce.py` does for Skills/MCP.
- **`permissions.demo_containment_ok`** (new, additive): a no-op for every real Orion user; for a demo-team actor, blocks any write targeting a non-demo-team Agent, regardless of role. This closes a real gap the existing team-scoped checks didn't cover - Reviewer/Admin roles intentionally bypass the team check everywhere else (ADR-0010's cross-team review design), which a public-facing demo Reviewer account must never inherit. Wired into all 7 real write paths a demo actor can reach (`create_agent_version`, `request_evaluation`, `request_promotion`, `approve_promotion`, `reject_promotion`, `grant_capability`, `revoke_capability`). See [ADR-0022](../adrs/0022-public-demo-sandbox.md) for the full reasoning.
- **Real safeguards on the demo's own external calls** (`app/services/evaluations.py::_enforce_demo_evaluation_guardrails`): evaluation requests from a demo actor may only target one fixed, known-safe `external_agent_version_id` (rejecting anything else with a real `422`), a 30s per-actor cooldown, and a 3-concurrent-evaluation cap across all demo activity - bounding real load on `agent-eval-api`/Cloud Tasks under public traffic.
- **Visibility bucketing**: the dashboard's counts/"Needs Attention" and the global promotion-request reviewer queue (`app/services/dashboard.py::_demo_visibility_clause`, `promotions.list_promotion_requests`'s new `actor` param) show a demo actor only the demo team's own data, and a real Orion actor never the demo team's - preserving full cross-team visibility for real Reviewers/Admins otherwise. The dashboard's recent-activity widget goes further and shows a demo actor nothing at all (real internal Orion audit history has no business reaching a public visitor); a real Orion actor's feed stays unfiltered, demo activity included, for full internal transparency. The dedicated `/activity` page and every entity's own detail-page activity sidebar are intentionally left unfiltered - ground truth stays ground truth, and per-entity views are already correctly scoped.
- **`app/services/demo.py::reset_demo_environment`**: never deletes anything (matching this platform's real no-deletion philosophy) - closes promotion requests abandoned >2h using the real `reject_promotion` path (actor: the existing shared system identity, `app/services/system_actor.py`, extracted this phase from the evaluation worker's private helper so the demo reset could reuse it instead of inventing a second system identity), and creates a fresh, unpromoted draft `AgentVersion` so a visitor always has somewhere to start. Two trigger paths to the same function: `POST /internal/tasks/demo/reset` (Cloud Scheduler, OIDC-verified the same way as the outbox sweep) on a 3-hour cadence, and `POST /v1/demo/reset` (real Admin-authenticated, on-demand).
- **`GET /v1/demo/status`** (unauthenticated, non-sensitive): the demo agent's id/name/team id and the one safe evaluation target - lets the frontend redirect somewhere useful after demo sign-in and pre-fill the evaluation-request form without a visitor ever needing to know/guess the target id.
- **Frontend**: `app/api/auth/login-demo/route.ts` (real Identity Platform sign-in, server-supplied credential, sharing `signInWithPassword` with the existing password-login route rather than duplicating it), `DemoLoginButtons.tsx` on `/login` ("Continue as demo Builder" / "Continue as demo Reviewer"), and a site-wide `DemoBanner` (root layout) shown only to a signed-in demo actor - names which Agent they're contained to and a one-click "Switch to demo Reviewer/Builder" role-switch, so a visitor can walk both sides of a promotion without ever typing a credential. The evaluation-request form (`EvaluationSection.tsx`) pre-fills (and locks, read-only) the external target for the demo agent specifically - a real UX gap found live during verification (see "Bugs found").

## Live end-to-end verification (all 10 steps, real deployed system)

1. Signed in via the real "Continue as demo Builder" button (real Identity Platform token minted server-side).
2. Used the sandbox `AgentVersion` (`sandbox-fd6b0833`) the scheduled reset had already created - there is no version-creation *form* in this product (manifest publishing is an API/CI operation by design, unchanged from Phase 5), matching the brief's own "creates/uses" phrasing.
3. Requested a real evaluation - the target field was pre-filled and read-only with the one safe stub id.
4. Real gate results rendered: 4/4 passed, a real `agent-eval` run id, completed in seconds via real Cloud Tasks delivery.
5. Requested production promotion - version was already `candidate`/`Eligible` from the real gate pass.
6. Switched to the demo Reviewer via the one-click banner button - a second, real Identity Platform sign-in.
7. Approved the request - real production transition, `CURRENT PRODUCTION` updated on the agent page immediately.
8. Verified resulting lifecycle and audit history: promotion history line ("requested by Demo Builder... decided by Demo Reviewer"), and the agent's own real-time activity sidebar (Version created -> Became candidate - gates passed -> Promoted to production).
9. Confirmed no-self-approval, live, via a direct API call: demo Builder created a second sandbox version, evaluated and requested promotion for it, then attempted to approve their own request - real `403 not authorized to decide this promotion request`.
10. Confirmed canonical Orion Commerce data was completely untouched: `incident-investigator`'s production version is still `4.3.4` (unchanged since Phase 6), verified via a real authenticated API call as Maya.

Two additional live containment proofs beyond the requested 10, targeting the exact gap ADR-0022 exists to close:
- The demo Builder attempted `POST /v1/agents/{incident-investigator}/versions` directly against the API (not through the UI, which never offers this) - real `403`.
- The demo Reviewer attempted to approve a real, still-pending Orion Commerce promotion request (`4.3.2`, left over from Phase 6's stale-block demonstration) - real `403`, proving the elevated-role cross-team bypass genuinely does not extend to the demo account.

## Bugs found

1. **The evaluation-request form has no way for a visitor to know the required `external_agent_version_id`.** Found live, mid-verification: the free-text field the real form already has (Phase 5) has no hint of what a valid value looks like for a portfolio visitor who has never seen `agent-eval`. Fixed by exposing the safe target via `GET /v1/demo/status` and pre-filling (read-only) the field specifically when the current Agent is the demo agent - real UX gap, real minimal fix, not present for any other Agent.
2. **The dashboard's global recent-activity feed leaked real internal Orion Commerce audit history to a signed-in demo actor.** Found live: after the first demo sign-in, the Overview page's "Recent activity" widget showed real Orion promotion/evaluation events (including a real error message from earlier Phase 6 failure-testing) to what will be a public account. Not a write-isolation break (the demo actor still could not act on any of it), but a real read-visibility leak given the feature's own stated goal ("isolate public demo activity from the canonical seeded portfolio data"). Fixed by suppressing the global feed entirely for a demo actor (see "Visibility bucketing" above) rather than attempting a generic, entity-type-spanning audit-event team filter, which `AuditEvent`'s polymorphic shape doesn't support cheaply.

## Tests

**Backend**: 196 passing (188 carried in from Phase 6 + 8 new, `tests/test_demo_sandbox.py`) - covering `is_demo_actor`/`demo_containment_ok` in isolation, a demo Builder blocked from writing to a real Orion agent, a demo Reviewer blocked from deciding a real Orion promotion request (the core gap this phase closes), the fixed-target and cooldown guardrails, and `reset_demo_environment`'s stale-request-closing and fresh-draft-creation behavior.

**Frontend**: 55 passing, unchanged from Phase 6. The new demo login route/banner/pre-fill behavior was verified live rather than unit tested - consistent with this project's existing, explicit convention (Phase 5/6 notes) of not unit-testing Next.js Route Handlers or components whose real behavior depends on the Next.js server/router runtime; the live E2E walkthrough above is the stronger proof for exactly this kind of code.

## Known limitations

- The temporary pending `PromotionRequest` created during the live no-self-approval test (step 9) was left in place deliberately, not manually cleaned up - the scheduled reset job will close it automatically once it passes the 2-hour stale threshold, the same real mechanism a genuinely abandoned visitor session would hit.
- No rate limiting exists on demo *sign-in* itself (only on evaluation requests) - a visitor can click "Continue as demo Builder" as often as they like. Not treated as a gap: sign-in itself does no real work and costs nothing beyond an Identity Platform token mint.
- The demo's containment relies on every future write path remembering to call `demo_containment_ok` - there is no single, structural enforcement point (unlike, say, a DB-level policy) that would catch an omission automatically. Documented as an accepted tradeoff in ADR-0022, not silently assumed safe forever.
